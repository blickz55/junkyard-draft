# Junkyard Draft: independent review before v0.5

Reviewed 2026-10-29 at commit `bc191b7` (released 0.4.0, rules version 2).

**Recommendation:** keep the existing architecture, complete a focused stabilization pass, then implement v0.5 in measured slices. The simulation foundation is sound enough to extend. Platform interaction, verification integrity, deployment packaging, and version migration need attention first. A passing suite currently misses several consequential failures.

This is a review and implementation handoff. No application source was changed. Fable 5.1 is treated as the user's choice of implementation agent; the repository itself uses TypeScript, Phaser, esbuild, Node, and Electron and contains no Fable dependency.

## Evidence and scope

- Read the project instructions, status, roadmap, design, continuation recipe, v1 plan/dossier, application source, tests, build tooling, verifier, desktop shell, and Control Room. Three parallel reviews covered verifier/telemetry, simulation/replay/storage, and UI/render/desktop; findings were reconciled with targeted probes.
- `npm run typecheck`: passed.
- `npm test`: **81 passed, 0 failed, 0 skipped**, approximately 45 seconds, including browser gameplay, rendering, Control Room, and the existing packaged desktop app.
- `npm run build`: passed; production bundle approximately 1,328 KiB.
- `npm run verifier:build`: passed from the complete repository.
- Inspected current browser screenshots of the build/keyboard state and results. The fixed desktop layout is coherent and legible at the tested size. This is limited visual evidence, not a fresh usability study.
- The first test run encountered restricted browser-cache, temporary-file, and loopback access. Rerunning with normal access passed completely; those initial failures are not reported as application defects.
- A real Docker image build was unavailable. Its source-copy layout was reproduced independently and the verifier bundle failed with the two missing imports described below. Packaged desktop tests exercised the existing release build; the review did not rebuild an installer or test installation on a clean PC.
- No new full balance campaign, hardware-GPU benchmark, external vulnerability audit, hosted-service test, screen-reader study, or human playtest was performed. Existing reports were assessed as historical evidence.

Priority meanings: **P1** should be fixed before extending the affected flow or exposing it publicly; **P2** belongs in the stabilization/v0.5 plan. A finding marked as a hosting prerequisite applies before public deployment even if local development continues.

## What to preserve

1. **The browser-free deterministic simulation.** Rules, seeded offers, action validation, and replay re-simulation are the project's strongest assets. Keep scoring independent of Phaser, UI state, animation, and wall-clock time.
2. **The RoundController extraction.** It provides a useful place to test round ownership, frozen layouts, playback, undo, and save behavior without a browser. Strengthen its transition ownership rather than moving logic back into GameScene.
3. **Server-derived scores and shared replay validation.** The verifier recalculates scores and the client rechecks fetched replays. Canonical identity needs repair, but this trust boundary is the right one.
4. **Write-before-memory persistence.** Atomic file replacement and the explicit 503 path are appropriate for a small, single-writer service.
5. **Small dependency surface and one build path.** Preserve the existing esbuild path and the authored atlas/procedural fallback. A framework rewrite would add migration work without resolving the identified problems.
6. **The test/tooling investment.** The suite meaningfully covers simulation conservation, legality, storage validation, failure persistence, renderer fallback, contrast, exports, and gameplay. The next improvement is realistic failure scenarios and release gates.

## Findings to address

### F01 — P1: malformed telemetry can terminate the verifier

Evidence: [event validation](<C:/dev/junkyard draft/game/src/telemetry/events.ts:54>) and [request-end handler](<C:/dev/junkyard draft/server/verify.ts:439>).

A batch with valid consent/install ID and an event object missing `name` reaches `JSON.stringify(undefined).slice(...)`, which throws. Validation runs outside the exception guard in the asynchronous request-end callback. A child-process probe exercising the actual request/data/end handlers exited with code 1.

**Fix:** make validation return a rejection for every possible JSON shape, and guard the entire asynchronous handler. **Accept:** omitted/null/numeric/object names, malformed timestamps/props, and arbitrary event objects receive a bounded 4xx response; a separate-process test proves `/health` remains available afterward. The existing malformed-URL test does not cover asynchronous body handlers.

### F02 — P1: the hook collector retains tokens it claims to redact

Evidence: [patterns and replacement](<C:/dev/junkyard draft/.claude/hooks/collect.mjs:18>), especially line 31.

Several patterns capture the entire secret as group 1. The shared replacement preserves group 1 and appends `[redacted]`, so a matching token becomes `original-token[redacted]`. Synthetic Anthropic-, GitHub-, and Slack-shaped tokens all remained intact in emitted records. These records feed the local event log/dashboard.

**Fix:** separate patterns that preserve a harmless label such as `Bearer ` from patterns that must replace the whole match. **Accept:** regression tests assert the original synthetic token is absent from every serialized output field; separately test authorization headers, key/value assignments, URLs with passwords, commands, responses, and error excerpts. No real credentials were used in this review.

### F03 — P1: property ordering bypasses replay duplicate detection

Evidence: [replay identity](<C:/dev/junkyard draft/server/verify.ts:66>) and [validated actions retain original objects](<C:/dev/junkyard draft/game/src/sim/replay.ts:35>).

SHA-256 is applied to the original action objects' JSON representation. Reversing the insertion order of an action's valid properties changes its hash while preserving exactly the same actions and score. Both copies were accepted and the board population increased to two. Extra action fields are already rejected; this defect concerns property order.

**Fix:** construct validated actions in an explicit field order before hashing and storing them. Preserve lookup of already-stored IDs where necessary. **Accept:** property-order permutations share one canonical identity and a second equivalent submission is rejected. This fixes representation-level duplicates; identity-based best-only boards remain a separate policy decision.

### F04 — P1: desktop text-entry flows use an unsupported API

Evidence: [player name](<C:/dev/junkyard draft/game/src/ui/TitleScreen.ts:24>), [custom seed](<C:/dev/junkyard draft/game/src/ui/TitleScreen.ts:55>), [replay import](<C:/dev/junkyard draft/game/src/ui/TitleScreen.ts:129>), and [first submission](<C:/dev/junkyard draft/game/src/ui/ResultsScreen.ts:103>).

The packaged Electron app throws `Error: prompt() is not supported.` Player naming, custom seeds, and replay import therefore fail. The first submission also disables Submit before invoking the prompt outside its try/catch, leaving a fresh desktop player unable to submit.

**Fix:** introduce reusable DOM text-entry dialogs and a selectable-text clipboard fallback. Ensure failed/cancelled submissions restore usable controls. **Accept:** a packaged-app test with a fresh profile enters a name and seed, imports a replay, completes a run, and submits to an isolated verifier. The existing smoke test plays one round through the dev API and misses these flows.

### F05 — P1: global keyboard capture breaks DOM controls and acts through Tips

Evidence: [capture and gameplay handlers](<C:/dev/junkyard draft/game/src/render/scenes/GameScene.ts:243>) and [Tips dialog](<C:/dev/junkyard draft/game/src/ui/TipsPanel.ts:53>).

Live Chromium probes confirmed: Enter on a focused draft offer does not activate it; Tab on the focused Tips button keeps focus there while selecting a bin part; Space with Tips open starts the underlying run. Capture is global and handlers do not respect DOM focus or the open dialog. Tips also lacks focus entry/trapping/restoration.

**Fix:** give the grid explicit keyboard focus/ownership, preserve native button/input behavior, suspend gameplay commands while dialogs are active, and manage modal focus. **Accept:** a keyboard-only path from title through draft, placement, Tips, run, and results uses actual focused controls. Opening Tips and pressing Space/arrows/Tab must not mutate the underlying run. Contrast and geometry tests should remain distinct from interaction-accessibility claims.

### F06 — P1 before hosting: the Docker source layout cannot build the verifier

Evidence: [Docker copy steps](<C:/dev/junkyard draft/Dockerfile:12>), [autoplayer import](<C:/dev/junkyard draft/server/verify.ts:44>), and [telemetry import](<C:/dev/junkyard draft/server/verify.ts:49>).

The image copies `game/src/sim` and `server`, but the verifier now also imports `tools/autoplay-lib` and `game/src/telemetry/events`. Reproducing the image's source layout made esbuild report both missing imports. The normal repository bundle test passes because those files exist outside that layout. The current Docker ignore file also excludes `tools`.

**Fix:** include the verifier's full source dependency graph in the image build context, adjusting both COPY and ignore rules. Alternatively move shared server-safe autoplay code into a deliberately included shared tree. **Accept:** CI actually builds the image, starts it, verifies health, accepts a legal replay, and confirms state survives a container restart with the same volume.

### F07 — P1 before hosting: public reads admit unlimited bot-par work

Evidence: [queue admission](<C:/dev/junkyard draft/server/verify.ts:269>), [par persistence](<C:/dev/junkyard draft/server/verify.ts:217>), and [read routes](<C:/dev/junkyard draft/server/verify.ts:409>).

Unauthenticated reads for new seeds enqueue expensive bot searches without a queue/admission cap. The failure map is unbounded and cached pars are not subject to `maxSeeds`. A probe queued 9,999 seeds behind one busy job; another configured `maxSeeds: 2` and persisted five par seeds.

**Fix:** cap computation admission and queue size, expire failure entries, bound cached pars, and prioritize today's seed. Serve ordinary reads even when new work cannot be admitted. **Accept:** saturation, deduplication, eviction, restart, and responsiveness tests. `BOT_PAR=0` is a temporary deployment option until admission is bounded. A worker timeout limits one job, not total requested work.

### F08 — P2: every accepted submission deletes cached bot pars

Evidence: [submission candidate](<C:/dev/junkyard draft/server/verify.ts:197>).

`submit()` constructs a board with `entries` and `replays` but drops `pars`. Confirmed: cached par 123 became null after one accepted submission and disappeared from the persisted file. All seed pars are affected, creating repeated work and unstable targets.

**Fix:** preserve the complete board state when creating candidates; use a common update helper to avoid dropping future fields. **Accept:** compute pars for multiple seeds, submit a replay, restart the verifier, and assert all pars are unchanged. The present test computes the par after submission.

### F09 — P2: Space during a watched summary can corrupt playback

Evidence: [Space handler](<C:/dev/junkyard draft/game/src/render/scenes/GameScene.ts:249>), [scheduled summary advance](<C:/dev/junkyard draft/game/src/render/RoundController.ts:174>), and [replay pump](<C:/dev/junkyard draft/game/src/render/RoundController.ts:193>).

Finishing a watched round schedules one advance. Manually advancing the summary schedules another, while the replay queue still contains its own boundary action. A controllable-scheduler probe of a six-round $228 replay finished with five recorded rounds, $190, phase `draft`, and playback already marked complete.

**Fix:** make phase advancement exclusively owned by playback while watching, and serialize/cancel stale scheduled callbacks. Do not consume boundary actions in incompatible modes. **Accept:** a controller regression and browser test press Space repeatedly around watched summaries and still finish exactly six rounds with the verified score.

### F10 — P2: local exports falsely claim verification

Evidence: [clip footer](<C:/dev/junkyard draft/game/src/render/clip.ts:122>).

The common painter always writes `junkyard draft · verified replay`. GIF and WebM exports are available for local results that have never been submitted, and the export API carries no provenance. This conflicts directly with the project's verification-label rule.

**Fix:** use a neutral footer, or pass verification provenance tied to the exact displayed replay. **Accept:** local exports carry no verification claim, and any verified export's provenance corresponds to the current run's accepted replay hash. Test the rendered footer for both export formats.

### F11 — P2: results can present an earlier attempt's standing as this run's

Evidence: [histogram identity selection](<C:/dev/junkyard draft/game/src/ui/ResultsScreen.ts:64>).

Results use this device's stored best submission for the seed, rather than the displayed run's identity. Submit attempt A, finish a different attempt B, and A's histogram bin/rank is shown beside B's score before B is verified. Even after submitting a lower-scoring B, storage may retain A. Overlapping requests also have no generation guard.

**Fix:** keep current-run verification state separately from per-seed personal bests. Explicitly label any previous best. Ignore responses belonging to an obsolete request/screen. **Accept:** two different-scoring attempts on one seed, a lower second submission, an unsubmitted second attempt, and delayed responses all display the correct provenance and standing.

### F12 — P2: opt-out can resurrect an in-flight telemetry batch

Evidence: [disable behavior](<C:/dev/junkyard draft/game/src/render/telemetry.ts:59>) and [flush completion](<C:/dev/junkyard draft/game/src/render/telemetry.ts:95>).

Disabling clears the queue, but a send that fails afterward unshifts its old events back into memory. Re-enabling can send those old events under a new install ID. A deferred-sender probe confirmed a pre-opt-out tip event was sent after disable/re-enable.

**Fix:** associate sends with a consent generation/install identity and discard stale completion effects. Abort outstanding transport where supported. **Accept:** delayed success/failure across opt-out/re-enable cannot restore or resend the old queue. A request already dispatched cannot be retroactively unsent; the regression concerns later queue restoration and transmission.

### F13 — P2: tutorial semantics already broke the stated rules-v2 compatibility guarantee

Evidence: [tutorial namespace](<C:/dev/junkyard draft/game/src/sim/run.ts:44>), [extra starter parts](<C:/dev/junkyard draft/game/src/sim/run.ts:85>), and the `v0.2.0` tagged implementation of the same module.

In v0.2, `tutorial-1` was a legal ordinary seed under rules 2. Current rules 2 turn every `tutorial-*` seed into constrained drafts and add three conveyors. A completed historical six-round replay using legal `pick i:1` actions scores $228 under the tagged implementation but now fails with `bad offer index`. The claim that every v0.2 replay still verifies is therefore too broad.

**Fix:** explicitly version scenario/tutorial semantics or establish a separately identified practice mode. Document the existing exception accurately; avoid another silent change under the same version. **Accept:** release-tag golden replays cover ordinary seeds and reserved-looking boundary names, and compatibility claims match the exercised corpus. The planned v3 transition needs an explicit policy for these historical files.

### F14 — P2: valid seed names collide with inherited object properties

Evidence: [seed dictionaries](<C:/dev/junkyard draft/game/src/render/storage.ts:49>), [best comparison](<C:/dev/junkyard draft/game/src/render/storage.ts:86>), and [submission comparison](<C:/dev/junkyard draft/game/src/render/storage.ts:101>).

`__proto__`, `constructor`, and `toString` are accepted custom seeds, but plain-object dictionaries and inherited-property checks treat them as existing records. Probes could store an ordinary seed's best/submission but retained neither record for these names.

**Fix:** use null-prototype dictionaries or Map and explicit own-property checks consistently through loading and recording. **Accept:** those seed names round-trip bests and submissions through storage as ordinary strings.

### F15 — P2: the shipping animation bypasses HiDPI base scaling

Evidence: [dock tween](<C:/dev/junkyard draft/game/src/render/scenes/GameScene.ts:613>) and [baseScale contract](<C:/dev/junkyard draft/game/src/render/atlas.ts:36>).

Packed art at DPR 2 uses scale 0.5 to occupy its logical size. Shipping tweens the dock to absolute scale 1.08, producing a target 2.16 times the normal displayed size. Existing HiDPI tests check initial geometry rather than an active ship animation.

**Fix:** multiply the animation target by the dock texture's base scale. **Accept:** shipping docks stay within the intended small pulse at DPR 1 and 2, including procedural fallback art. This is supported directly by the scale calculation; no hardware-GPU claim is implied.

### F16 — P2 product gap: Full Grid cannot be earned legally

Evidence: [badge condition](<C:/dev/junkyard draft/game/src/sim/badges.ts:31>), [inventory/rules](<C:/dev/junkyard draft/game/src/sim/rules.ts:8>), and [synthetic badge test](<C:/dev/junkyard draft/tests/badges.test.ts:35>).

The badge requires all 48 cells occupied, but normal play supplies five starter machines plus six picks: at most 11 machines, or 14 in the tutorial. The test fabricates a 48-machine layout outside the legal acquisition path.

**Fix:** redefine the achievement around attainable play or defer it to a mode that supports the required inventory. **Accept:** every advertised badge has at least one legal action sequence that earns it. Do not introduce dozens of extra machines solely to satisfy this badge.

## v0.5 prerequisites and design recommendations

### Separate records by rules version before introducing v3

[Storage schemas](<C:/dev/junkyard draft/game/src/render/storage.ts:19>) have no rules version for bests/submissions; [only unfinished saves](<C:/dev/junkyard draft/game/src/render/storage.ts:75>) are version-filtered. After the proposed 2→3 bump, a high v2 best remains the displayed target, and an old higher submission can prevent a lower v3 result from replacing its hash. The v3 board then cannot find the device's stored v2 identity.

Partition bests, submissions, cached targets, and any score-derived progress by rules version. Specify whether old results are archived or hidden. Preserve settings, player name, onboarding, and days played where their meaning does not depend on scoring. Provide a clear old-save/replay explanation and test an actual v2 profile upgrading to v3.

### Make the Sieve earn its place before committing the milestone to it

Mixed materials are possible by merging processed and raw branches, but a straight factory line does not naturally produce them. With at most 11 machines on 48 cells, a sorting detour has an unproven advantage over simply keeping routes separate.

First author a same-inventory mixed-input puzzle and compare a Sieve solution with the strongest simple separated routes. Demonstrate a routing/cell/throughput tradeoff that a player can understand. Include raw scrap and every processed material, all orientations, blocked chosen exit, simultaneous contention, jam reporting, and conservation. If there is no convincing benefit, revise or defer the machine rather than tuning toward an arbitrary pick-rate band. This is a design hypothesis, not a claim that a Sieve can never be useful.

### Generalize the measurement tools before using them as acceptance gates

[Balance tooling](<C:/dev/junkyard draft/tools/balance.ts:23>) is hard-coded to the Press and its hold/value variants. It cannot currently certify Sieve balance or reroll economics. [The search](<C:/dev/junkyard draft/tools/autoplay-lib.ts:13>) accepts only strict score improvements; useful routing changes requiring neutral or temporarily worse intermediates can be invisible. Its [dead-end definition](<C:/dev/junkyard draft/tools/autoplay-lib.ts:91>) is four or more flat rounds, while the plan describes no improving draft in any round.

Add machine selection, separate RNG streams for search and offers, reroll policy/cost accounting, rule/build/search-budget metadata, per-seed paired deltas, and reproducible output. Save candidate/banned action lists and replay-verify them. Investigate negative deltas: a bounded greedy bot getting worse is not proof that the expanded legal choice set is intrinsically worse. Keep a valid baseline policy available as a control and report heuristic search quality separately.

Make pass/fail thresholds executable with nonzero exit status. Define the score sanity bound from legal acquisition/output limits and sell bonuses; the present suspicious-score expression is a diagnostic heuristic. Store v0.5 reports under a v0.5/rules-3 baseline directory, not the v0.3 directory carried over in PLAN-v1.

### Treat reroll as a complete replay/state/accounting feature

Keep its RNG purpose-specific so using it cannot change later rounds. Specify phase restrictions, one-per-round state, affordable boundary, duplicate prevention, tutorial behavior, and whether a reroll may return the same set/order. Spending score means result/share/clip accounting must explain `production + sales − reroll cost`; current result accounting was written for production plus sales.

Put cost, eligibility, and state in the pure simulation. Extend validation, replay encoding, undo reconstruction, save/resume, controller notifications, telemetry, and autoplayer together. Test cost−1/cost/cost+1, repeated reroll, illegal phases, round resets, identical future offers, export/import, server verification, and interruption/resume. A UI-only reroll would compromise replay authority.

### Derive tie-breakers from the replay and keep them visible

Compute final-round machine count during verification; never accept the count from the submitted payload. Use one comparator for boards, histogram ranks/neighbours, replay retention, pruning, and returned personal rank. Persist derived counts or specify how old entries are migrated. Add a final deterministic ID fallback if server receipt timestamps match. Explain equal-score ordering next to boards while keeping percentile semantics clear about equal scores.

The machine-count tie-breaker is a secondary optimization objective, even if score remains the headline. Validate that players understand this interaction with Minimalist and final-round unplacement. Do not silently change the meaning of Clean or other badges while adding Sieve jam behavior.

### Resolve plan/versioning contradictions before the first rules PR

[PLAN-v1's v0.5 section](<C:/dev/junkyard draft/docs/PLAN-v1.md:85>) says to bump rules only after the sweep, while project instructions require every rules change to carry a version change. Use an isolated v3 integration branch or explicit unreleased rules identity from the first semantic change; do not publish incompatible new rules as v2. Also do not keep changing a publicly distributed v3 ruleset without a new identity.

Write PLAN-v2 with exact source-of-truth rule values, acceptance tests, data migration, deployment order, and rollback behavior. Current rules use slag $1; some historical test names/changelog statements still say $2. Keep historical records clearly historical and remove misleading current claims. STATUS's current next task is planning, so the handoff should explicitly authorize the stabilization work before the revised feature sequence.

## Release and maintainability improvements

- **Make CI exercise correctness.** The only committed workflow is [the perf job](<C:/dev/junkyard draft/.github/workflows/perf.yml:12>); it runs neither the full test suite nor typechecking. Add install, typecheck, tests, web build, verifier bundle, and image smoke checks. Use a Windows job that actually packages and exercises the desktop app for release candidates.
- **Arm the performance gate.** No committed `perf-ci.json` baseline exists. The workflow explicitly passes without one. Its newest-directory selection can disable an older baseline when a newer directory is added. Select an explicit baseline or latest existing baseline file.
- **Reject missing perf evidence in CI.** [The comparator](<C:/dev/junkyard draft/tools/perf-gate.ts:17>) returns success for an empty report and for entirely unmatched labels; probes confirmed both. Require nonempty samples, valid metrics, and expected matching labels in CI, while allowing optional extra local samples.
- **Add a release-tag replay corpus now.** Include ordinary, tutorial-looking, boundary-name, sold-part, press, undo/redo, and long-action examples. Run replay verification across Node and at least two browser engines before v3 release. A small corpus is more valuable now than deferring every compatibility check to v0.8.
- **Keep the single-writer service assumption explicit.** Atomic rename prevents partial files, but does not coordinate two verifier processes. Full synchronous JSON rewrites also become costly well before theoretical maximum counts. Measure persisted bytes and write latency; add backup/restore and restart tests before scaling storage. A database migration is conditional on measured need.
- **Bound Control Room lifetime state.** The feed is capped at 3,000, but tool-call history and several other collections keep growing. A synthetic 5,000-tool probe retained 5,000 tool records. Add retention/compaction and handle malformed URL/percent decoding without process failure. Its file-serving containment uses a string-prefix check at [server line 116](<C:/dev/junkyard draft/control-room/server.mjs:116>); use path-boundary-aware containment. These are local-tool hardening items, not a demonstrated public compromise.
- **Clean up scene ownership.** The global blur handler at [GameScene line 262](<C:/dev/junkyard draft/game/src/render/scenes/GameScene.ts:262>) is registered on each scene creation without explicit teardown. Use named handlers removed on shutdown and cancel scene-owned asynchronous work. Continue extracting cohesive responsibilities only when it improves testability; avoid a broad GameScene rewrite.
- **Keep Electron's isolation settings.** Before wider distribution, restrict navigation and validate IPC sender, payload size/type, filename extension, and destination behavior for clip saves. The review demonstrated broken prompts, not a remote code execution exploit.
- **Prioritize real playtests.** The tutorial, text density, mixed-material decision, and reroll cost need observation with fresh players. Software-rendered browser timings and a contrast audit do not establish hardware-GPU performance or screen-reader usability. Maintain the existing clean-install, low-end-device, and hosted-verifier checks as explicit release evidence.

## Recommended order for Claude

1. **Stabilization A: verifier and collector integrity.** Fix F01–F03, F08, and F12. Add focused regressions and canonical board-update handling. These should not change scoring rules.
2. **Stabilization B: desktop, input, and provenance.** Fix F04–F05 and F09–F11, then F14–F15. Exercise fresh desktop profiles and actual DOM keyboard focus. Address F16's unreachable badge deliberately.
3. **Deployment readiness.** Fix F06–F07, enable correctness CI, arm/validate performance evidence, and prove restart persistence before hosting. Keep service deployment reviewable as a separate change.
4. **v0.5 foundation.** Resolve F13 and the rules/scenario identity policy; partition score records; add the golden corpus; generalize the balance tool; write PLAN-v2 with explicit migration and release gates.
5. **Gameplay experiments.** Prove the Sieve fixture first. Implement Sieve plus tiered offers as one coherent rules experiment, then reroll with complete replay/accounting support. Measure each independently before combining them. Derive and display the tie-breaker consistently.
6. **Release candidate.** Run the full suite, build/package checks, version-migration corpus, fresh-profile interaction paths, paired balance sweeps, exploit bounds, keyboard/modal checks, clip provenance, and a small human playtest. Record actual evidence and remaining limitations in STATUS/ROADMAP.

Keep these as small reviewable PRs with explicit acceptance criteria. Preserve the current working game while collecting enough evidence to decide whether each new decision improves it. Hosting and social expansion should follow service integrity and an observed player need; they need not be bundled into the first v0.5 rules increment.
