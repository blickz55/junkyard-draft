# PLAN-v3 — v0.6 "The daily, done right", re-cut after 0.5.0

Written 2026-10-29 at `main` after the 0.5.0 release (rules version 3). It replaces the v0.6 section of `docs/PLAN-v1.md`; v0.7 onward stays as PLAN-v1 describes until PLAN-v4. Same format as PLAN-v2: binding policies first, then numbered, sized increments with *What / Why / Accept*. Sizes: S ≤ half a day, M a day or two, L longer. ⚑ needs a human. **No rules change in v0.6**: `RULES_VERSION` stays 3, every increment is replay-compatible, and the verifier's protocol grows additively.

## 0. Where we start

Shipped: a verified board per seed with a derived tie-breaker, bot par, histogram and percentile, replays for the top 100, opt-in funnel events, the Docker image and CI smoke, records partitioned by rules version. Open from before: the verifier is not hosted (0.4.7 ⚑), so every "verified" number in the game today is a local one. The review's integrity notes that bind this milestone: server-minted seeds with published commitments, one best entry per identity, per-player submission buckets beside the per-IP limiter, and an explicit data and deletion policy before anything social. DOSSIER-v1 §5.1 (identity, data model, endpoints, abuse answers) and §6 (web first, hosting shape) are the design source.

## 1. Policies that bind every increment

**Hosting is the gate for ranked play.** A server-minted daily only means something when one server mints it for everyone. Until 0.4.7 ⚑ is done, every increment here is built and tested against the local verifier and CI's image, the title keeps saying "local verifier", and the client-derived `daily-YYYY-MM-DD` seed stays as the practice seed. Nothing in v0.6 may remove the local path: a player with no server still has today's practice daily, local bests and the archive of their own runs.

**Identity.** A 128-bit random device token, generated on first launch and stored with the other version-independent settings (browser storage; Electron keeps it in `userData` through the preload bridge). `player_id = SHA-256(token)` hex. The token is the only secret: it travels only as a bearer header on POSTs over TLS, it is never logged, and the verifier stores only its hash. Display name stays a label; a four-character tag derived from `player_id` disambiguates (`Jon#7Q2M`). A recovery code is the token in base32 groups, shown once on request and importable on another device. Legacy anonymous entries (no `player_id`) remain on boards unchanged and can never be claimed. One best entry per `(seed, player_id)`: a better verified run replaces the worse one (and its stored replay); an equal or worse run is accepted as verified but not recorded as an entry. Steam tickets (v0.8) bind to the same `player_id` later.

**Data and deletion.** Stored personal data: name, tag, `player_id`, replays, scores, verified-at times, consented funnel events, and the daily-salted IP hash for 7 days. `DELETE /me` (bearer) removes the name, anonymises entries and deletes replays. No email, no cookies, no third parties. The policy page (0.6.5) is generated from the same constants the code uses.

**Protocol compatibility.** Endpoints grow additively and are versioned by behaviour, not URL: a 0.5.0 client keeps working (anonymous `POST /verify`, client-derived daily) for one release. Server and client ship from the same commit; the server's `/health` carries `protocol: 2`.

**Storage.** The board stays a single JSON file behind the atomic-write path for v0.6, with two new top-level sections (`players`, `dailies`). 0.6.7 measures bytes and rewrite latency with synthetic load and sets the hard trigger for the SQLite move (PLAN-v1 0.8.7): above 5 MB or 50 ms per rewrite on the VPS, 0.8.7 moves forward. Single writer only; the runbook says so.

**Abuse baseline** (DOSSIER-v1 §5.1): per-player bucket (2 submissions per minute) beside the per-IP limiter; name normalisation (confusables, repeated characters, length) and a small server blocklist at claim time with a rename cooldown; duplicate-hash rejection as today; report-then-hide and moderation tooling stay in v0.9.

**Evidence.** Every increment: unit tests on the verifier, an e2e against a spawned verifier where the client changed, the Docker smoke extended when an endpoint is added, STATUS numbers, and no fabricated populations anywhere (the archive and medals show only what was verified).

## 2. The increments, in dependency order

**0.6.0 Identity without passwords** — M. *What:* client token and `player_id`; `POST /identity` (bearer; claims or renames the display name after normalisation and blocklist, returns `{ playerId, name, tag }`; rename cooldown 24 h); `GET /identity` (bearer; who am I); `POST /verify` reads the bearer when present and stamps the entry with `player_id`, `name#tag`; keep-best per `(seed, player_id)` on submit (the replaced entry's replay is dropped, the better one kept; retention unchanged); the title's "Set player name…" becomes "Player: Jon#7Q2M" with a dialog that also offers "Show recovery code" and "Restore from code"; `jd.player` migrates into the first claim; `jd.submissions` keeps working as the device's own index. Anonymous submissions remain possible when the server has no identity for the token (first launch offline). *Why:* zero-friction stable identity is the ladder's first rung (PLAN-v1 0.6.1); one entry per identity is what makes a board a board. *Accept:* verifier tests — tag derivation deterministic and distinct for distinct ids, claim/rename/cooldown, normalisation and blocklist refusals, keep-best replaces a worse entry and keeps the better replay, an equal run is verified but not recorded, legacy anonymous entries untouched and never claimable, per-player bucket enforced, bearer never logged; e2e — claim a name, submit twice with a better second run and see one entry; export and restore the recovery code in a fresh context and keep the identity; Docker smoke claims a name and submits with the bearer.

**0.6.1 Server-minted daily seed with a published commitment** — M. *What:* `DAILY_SECRET` (env; the runbook says to generate and back it up) → `seed(date) = "daily-" + date + "-" + base32(HMAC-SHA256(secret, date))[0:8]`; `GET /daily` serves today's seed only after 00:00 UTC together with `commitment = SHA-256(seed(tomorrow))` and yesterday's seed for verification; a `dailies` record per date `{ date, seed, commitment, issuedAt, closesAt, rulesVersion, build }`; a submission counts for the daily board only if its seed is an issued daily seed within its window (any other seed is an ordinary seed board, as today); the client fetches the seed when "Today's challenge" is pressed and falls back to the practice seed `daily-YYYY-MM-DD` labelled "practice (unranked)" when the server is unreachable or the day has not opened. *Why:* the client must generate offers, so fairness rests on the seed being unknowable before the window (PLAN-v1 0.6.2). *Accept:* tests — seeds differ per date and per secret, the commitment published on day D verifies against the seed served on D+1, a request before 00:00 UTC for tomorrow is refused, a submission on the practice seed never reaches the daily board; e2e — title shows the minted seed from the spawned verifier and the practice label when the verifier is down; the rehearsal script gains "rotate the secret: old days still verify by their stored seed".

**0.6.2 The 48-hour window, freeze, archive** — M. *What:* `closesAt = D+2 00:00Z`; at freeze the day's board is marked `frozenAt` and no further entries join it (a late submission is verified and answered with `late: true`, visible to the player, never ranked); `GET /archive?from=&to=` lists frozen days with seed, N, par, medal thresholds (0.6.4) and the top five; the title strip shows "closes in 31 h" and "provisional" until freeze; an "Archive" fold-out lists past days, each playable as practice with its frozen histogram and replays. *Why:* one global deadline for everyone, catch-up without leaks (PLAN-v1 0.6.3). *Accept:* tests — window arithmetic at the boundaries, freeze is idempotent and survives a restart, late submissions answer `late` and stay off the board, the archive is sorted and paged; e2e — a day frozen by a test clock shows "final" and its archive entry.

**0.6.3 Days played and streak, with grace** — S. *What:* the client keeps the UTC dates of its verified daily submissions (already `jd.days.v1` for days played; add `jd.dailystreak.v1`); streak = consecutive dates, where a submission inside the day's 48-hour window extends the day before; display "17 days played · 5 in a row"; a break shows the new count with no loss copy, no colour, no notification; reminders are not in v0.6 (an opt-in desktop notification is v0.8 work). *Why:* decoupled, forgiving streaks retain without punishing (PLAN-v1 0.6.4). *Accept:* unit tests on the streak function (gaps, the grace window, timezone independence, idempotence); the title line; the detailed share variant line "17 days · 5 in a row" appears only when the streak ≥ 2.

**0.6.4 Medals after close** — S. *What:* at freeze the verifier computes bronze/silver/gold as the 50th/80th/95th percentiles of the day's verified scores (published on the archive entry and the policy page), stores them on the `dailies` record, and `/archive` and `/histogram` return them; the client shows the medal on the archive entry and in the detailed share variant for frozen days; bot par stays the day-of target. *Why:* targets far down the board (PLAN-v1 0.6.5). *Accept:* verifier test on a synthetic distribution (ties, N < 5 → no medals, exact percentile math documented); client renders only when the server sent thresholds.

**0.6.5 Fairness and verification policy page** — S. *What:* `tools/make-policy.ts` generates `game/public/policy.json` from `rules.ts`, the verifier's constants (`TIE_BREAK`, retention, window, medal percentiles, rate limits) and the identity/data policy text; a title and results link opens an in-game panel (DOM) rendering it; a static `docs/POLICY.md` is generated from the same source. *Why:* transparency is a fairness rule and prevents drift (PLAN-v1 0.6.6). *Accept:* a test regenerates the JSON and diffs it against the committed file; the panel shows the current rules version and the tie rule.

**0.6.6 Reveal other players' daily replays only after you submit or the day closes** — S (moved up from PLAN-v1 0.7.6 because it is integrity, not social). *What:* on an open daily, "Watch #1" and board replay buttons are disabled until the viewer has a verified entry for that day or the day is frozen; archive days are always watchable; the server enforces the same rule on `/replay` for daily seeds (bearer or frozen). *Why:* unlimited attempts plus visible replays is the fairness leak (PLAN-v1 0.7.6). *Accept:* e2e — disabled before, enabled after a submission; verifier test — `/replay` for an open daily without a qualifying bearer answers 403 with the reason.

**0.6.7 Storage measurement and the SQLite trigger** — S. *What:* `tools/board-stats.ts` reports entries, replays, bytes and the last rewrite latency; a synthetic load (50 000 entries over 365 dailies) run against the file store on the VPS once hosted; the hard trigger (5 MB or 50 ms) written into `server/README.md`; a `backup`/`restore` note (copy the file; the runbook). *Why:* the review asked for measured need before a database. *Accept:* the tool runs in CI against a synthetic board; the numbers are in STATUS.

**0.6.8 ⚑ Host the verifier and open the web beta** — human (0.4.7 ⚑ plus DOSSIER-v1 §6's first three actions): register `junkyarddraft.com`, stand up one small VPS with Caddy and the Docker image (`DATA_DIR` on the volume, `DAILY_SECRET` generated and backed up, `CORS_ORIGIN` = the site), bake `VERIFIER_URL` into the web and desktop builds, deploy the web build to Cloudflare Pages, run the game e2e's daily submission against the hosted URL and record it in STATUS. Everything above is testable without it; nothing above is *true* for players until it is done.

## 3. What the nightly routine may take

0.6.0–0.6.7 are `main` work with no rules change; each is one PR that changes client and server together where the protocol grows, and extends the Docker smoke when it adds an endpoint. 0.6.8 is the owner's. Anything from PLAN-v1 v0.7 (challenge links, groups, forks, weekly modifiers, Discord) waits for PLAN-v4 and for the hosted verifier.

## 4. Metrics and risks

Watch: share of daily players who submit at least one verified run (target ≥ 60 % of those who finish a daily), median attempts per submitter (1–3), 7-day distribution of days played, weekend dip, late-submission rate (how many hit the window edge). Risks: the minted seed makes the ranked daily depend on the server at 00:00 UTC (fallback: the labelled practice seed; the title never pretends); tokens are lost with cleared storage (recovery code now, Steam binding at v0.8); a 48-hour window delays "final" by a day (the UI says "provisional" until freeze); the JSON board grows with identities and dailies (0.6.7 measures; the SQLite trigger is written down, not guessed).
