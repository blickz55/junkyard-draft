# PLAN-v2 — v0.5 "Decisions", re-cut after 0.4.0 and the pre-v0.5 review

Written 2026-10-29 at `main` after the stabilization pass (`docs/reviews/PRE-V05-REVIEW-2026-10-29.md`, ROADMAP M7). It replaces the v0.5 section of `docs/PLAN-v1.md`; v0.6 onward stays as PLAN-v1 describes until PLAN-v3 is written. Format as PLAN-v1: numbered, sized increments with *What / Why / Accept*. Sizes: S ≤ half a day, M a day or two, L longer. ⚑ needs a human.

## 0. Where we start

Shipped: everything PLAN-v1 lists for v0.3 and v0.4 (0.4.0, rules version 2) plus the stabilization slices A–D. What the review asked for before the first rules change is still open and is the front of this plan: records partitioned by rules version, a generalised balance tool with executable gates, evidence that the Sieve earns its slot, reroll designed as replay-authoritative state, a derived tie-breaker, and an explicit rules-identity, migration and rollback policy. Nothing in v0.5 is social; the social horizon (DOSSIER-v1 §5.1) starts in v0.6.

## 1. Policies that bind every increment

**Rules identity.** `RULES_VERSION` is 2 on `main`. All v0.5 rules work happens on one integration branch, `rules-v3`, whose first commit sets `RULES_VERSION = 3`; the branch never deploys to a public verifier and its builds show "rules v3 (preview)" on the title. `main` stays playable and verifiable as v2 until the release increment (0.5.6) merges the branch. This resolves the PLAN-v1 instruction to "bump after the sweep" against `CLAUDE.md`'s "bump on every rules change": the bump is the branch's first act, the sweep decides whether the branch merges. Changing a published v3 again later needs v4, never a silent edit.

**Scenario namespaces** (`tutorial-*`, any future reserved prefix) are rules (DESIGN.md policy, review F13). Changing them bumps the version.

**Record partitioning.** Local bests, submissions and any score-derived progress are stored per rules version from 0.5.0 on. Old results are archived, not deleted: the title shows the current version's bests as the headline and a collapsed "Under rules v2" block for the previous ones. Settings, player name, onboarding state, read tips and days played are version-independent and survive. Saves of an unfinished run are already version-filtered (`loadSave`).

**Verifier data.** The verifier already stores `rulesVersion` per entry and par, ranks only the current version and refuses other versions on `/verify` with the version in the message. v3 adds derived tie-breaker data to entries (0.5.5); entries without it rank last among equal scores until their stored replay is re-derived at startup. Nothing is rewritten in place; a deployment writes a new file version marker.

**Deployment order (release day).** 1) merge `rules-v3` to `main`, tag `v0.5.0`; 2) deploy the verifier bundle (it now accepts only v3); 3) publish the web build and the desktop installer the same hour; 4) the title shows a one-release banner "Rules changed to v3: v2 replays and saves no longer verify; your v2 bests are kept under 'previous rules'". **Rollback:** redeploy the previous verifier bundle and web build; v3 entries stay in `board.json` under their version and never rank for v2 clients; no data is lost either way. The runbook is written in 0.5.6 and rehearsed once against a local verifier.

**Evidence.** Every rules increment carries: sim tests, a golden corpus regeneration (`tools/make-golden.ts`, with the v2 corpus moved to `tests/golden/archive/v2/` and a test that those files are refused with the version message), a paired balance report under `docs/baselines/0.5/`, and a DESIGN.md decisions entry with the numbers. Thresholds are executable (nonzero exit), not prose.

## 2. The increments, in dependency order

**0.5.0 Partition local records by rules version** — S/M, on `main` (no rules change). *What:* `storage.ts` schema `jd.bests.v2`/`jd.submissions.v2` keyed `{ byVersion: { "2": Bests, "3": Bests } }` with a one-time migration from the current `jd.bests.v1`/`jd.submissions.v1` shape into the `"2"` slot; `loadBests()`/`loadSubmissions()` take the current version; `loadArchivedBests()` returns the others for the title's collapsed block; `recordBest`/`recordSubmission` write under `RULES_VERSION`. Keep null-prototype dictionaries (review F14). The results screen's `matchesStoredSubmission` and the title's daily rank read the current version only. *Why:* after the bump a v2 best would otherwise remain the displayed target and an old higher submission could block a lower v3 result from replacing its hash (review, v0.5 prerequisites). *Accept:* `tests/storage.test.ts`: a captured real v2 profile (localStorage dump checked in under `tests/fixtures/profile-v2.json`) upgrades with bests, submissions, settings, name, tips and days intact; writing under version 3 leaves the v2 slot untouched; the title e2e shows the archived block once a second version exists; the upgrade is idempotent.

**0.5.1 Generalise the measurement tools** — M, on `main`. *What:* `tools/balance.ts --machine <kind> --variants <file.json> --seeds N --tries T --json out --gate` (per-seed paired deltas baseline vs ban vs each variant; metadata: rules version, build, search budget, seeds, rng streams; candidate and banned action lists saved and replay-verified before counting; nonzero exit when a `--gate` threshold fails: "0 seeds worse", mean lift > 0, pick-rate band). `tools/autoplay-lib.ts`: separate RNG streams for search and for offers (`${seed}:search:${k}` vs the sim's `${seed}:draft:${round}`), a neutral-move acceptance option (equal-score moves accepted with probability p so routing setups that pay off later are reachable) reported separately from the greedy baseline policy which stays as the control, a `--reroll-policy` hook (0.5.4), the dead-end definition aligned with PLAN-v1 ("no improving draft in any round"), and the score sanity bound derived from legal acquisition/output limits plus sell bonuses instead of the current heuristic. `tools/autoplay.ts` writes under `docs/baselines/0.5/`. *Why:* the tool is hard-coded to the press and cannot certify a Sieve or reroll economics; a greedy bot getting worse under a wider choice set proves nothing about the rules (review). *Accept:* `tests/balance-tool.test.ts` runs a 3-seed × 10-try job on the press and asserts the JSON shape, paired deltas, metadata and that `--gate` exits 1 on a synthetic failing threshold; the neutral-move search reaches a layout the greedy one misses on a constructed seed; both policies' reports are byte-identical across two processes.

**0.5.2 Prove the Sieve fixture** — S, on `rules-v3` behind `RULES.experimental.sieve` (design evidence before design commitment). *What:* implement the Sieve in the sim as PLAN-v1 0.5.1 describes (1 cell, input from behind, raw scrap forward, processed materials to the oriented side, blocked chosen exit waits = jam) but not yet in the draft pool; author a same-inventory mixed-material puzzle (hopper + crusher branch merging with a raw branch into one furnace line, 11 machines on 48 cells) and compare the best Sieve solution against the strongest separated-route solutions found by the 0.5.1 search with neutral moves. Document the tradeoff (cells spent versus slag avoided) in `docs/DESIGN.md` with the numbers. *Why:* a straight line never mixes materials; with at most 11 machines a sorting detour has an unproven advantage over separate routes (review). *Accept:* `tests/sieve-fixture.test.ts` (branch only): both exits, all five materials, all four orientations, blocked-exit wait reported as a jam, conservation; the fixture's Sieve solution earns at least 10 % more than the best separated route the search finds within the same inventory, or the test records "no convincing benefit" and 0.5.3 is deferred to PLAN-v3 with the Sieve replaced by a different decision (candidates: a Buffer cell that holds one item to smooth press feeding; a Dock bonus for alternating materials). The go/no-go is a written decision in DESIGN.md either way.

**0.5.2 result (2026-10-29): no-go.** The fixture's separated routes beat the Sieve line by 17 % with the same eleven machines, and still beat it if a dock paid double for ingots; the Sieve stays in the sim as an experimental kind and is not offered. The decision machine for v0.5 is the **Tuner** (below); the Sieve text in 0.5.3 is kept for the record. See `docs/DESIGN.md`.

**0.5.3 (re-cut) Tuner in the pool + round-tiered offers** — M, `rules-v3`. *What:* a 1-cell Tuner with no input or output: every orthogonally adjacent processor (crusher, furnace, press) holds items one tick less (minimum one tick); two Tuners do not stack on the same processor; it occupies a cell and a draft slot. Draft weight ~10, offered from round 3 through the tier table (rounds 1–2: the seven 0.2.0 machines, round 1 still guarantees a crusher), identical for every player on a seed; card art (`m-tuner`), badge strings, machine advice, a tip with a live demo, autoplayer support (the search places it like any part; its value shows through the processors' throughput). *Why:* the bottleneck of every good line is a processor's hold time, so a Tuner is a pure throughput-for-space decision that composes with everything; it needs no new material, no new routing rule and no sorting, and the fixture work above showed that routing machines cannot earn their slot on this grid. *Accept:* sim tests: adjacency on all four sides, non-stacking, minimum one tick, no effect on conveyors/splitters/docks/hoppers, conservation; pool tests as before; `tools/balance.ts --machine tuner --gate`: picked in 25–50 % of rounds offered, 0 seeds worse when allowed vs banned, mean lift > 0; golden corpus regenerated. Original Sieve text follows for the record. *What (Sieve, superseded):* if 0.5.2 says go: Sieve joins `RULES.draftWeights` (~10) and the tier table in `rules.ts` (rounds 1–2: the seven 0.2.0 machines, round 1 still guarantees a crusher; from round 3 the Sieve and future advanced machines), identical for every player on a seed; card art (SVG + atlas key `m-sieve`), badge strings, machine advice, a tip with a live demo, autoplayer support. Clean's definition is stated explicitly: a Sieve waiting on a blocked exit is a jam tick and forfeits Clean, like any other wait. *Why:* PLAN-v1 0.5.1/0.5.3 reasoning (filter earns its slot only with ≥ 2 materials in flight; tiering is onboarding and escalation, seed-fair). *Accept:* sim tests as 0.5.2 plus pool tests: snapshot of offers for 50 seeds × 6 rounds, the seven 0.2.0 machines never excluded from any round, Sieve never offered before round 3; `tools/balance.ts --machine sieve --gate`: picked in 25–50 % of rounds offered, 0 seeds worse when allowed vs banned, mean lift > 0; autoplayer sweep finds no score above the derived sanity bound; art/tip/advice e2e anchors present; golden corpus regenerated for v3 with v2 archived.

**0.5.4 Reroll as replay-authoritative state** — M, `rules-v3`. *What:* new action `{ t: 'reroll' }` in the sim: draft phase only, once per round (`RunState.rerolledRound`), cost `RULES.rerollCost = 40` deducted from `score` (refused as illegal when `score < cost`), new offers from the purpose-specific stream `${seed}:draft:${round}:reroll:1` (so later rounds never change and a reroll cannot be used to fish future offers), the same set or order may legitimately recur, disabled on `tutorial-*` seeds (a scenario rule, versioned). Everything that reads actions learns it together: `validateAction`/`canonicalAction`, replay encoding, undo reconstruction (a reroll is undoable only until the pick), save/resume, `RoundController` notifications, telemetry (`reroll_used`), the autoplayer's `--reroll-policy`, the results accounting line `production + sales − rerolls`, share detailed variant and clip strip. UI: a "Reroll (−$40)" button on the draft card with the cost and remaining balance. *Why:* one wallet that is also the score (LocalThunk's lesson, PLAN-v1 0.5.2); a UI-only reroll would compromise replay authority (review). *Accept:* sim tests: cost−1 refused, cost accepted, cost+1 accepted; second reroll in a round refused; reroll in build/run/summary refused; rerolling in round 2 leaves rounds 3–6 identical to a non-reroll run; tutorial refusal; export/import round-trip and verifier acceptance; interruption (save after reroll, resume shows the rerolled offers); controller undo/redo; golden corpus gains a reroll replay; `tools/balance.ts --reroll-policy greedy --gate`: autoplayer rerolls in 10–30 % of rounds and no seed's best drops.

**0.5.5 Tie-breaker derived from the replay** — S, `rules-v3`. *What:* the verifier computes `finalMachines` (machines placed in round 6) while re-simulating a submission and stores it on the entry; never accepted from the payload. One comparator `byRank = score desc, finalMachines asc, verifiedAt asc, replayHash asc` used by boards, histogram ranks and neighbours, replay retention, pruning and the returned personal rank. At startup, entries lacking the field are derived from their stored replay when present, otherwise rank last among equals. The rule is printed under every board and on the results screen; the percentile keeps its "strictly lower score" meaning. *Why:* PLAN-v1 0.5.4; the review's insistence on derivation, one comparator and a deterministic final fallback. *Accept:* verifier unit tests on three equal-score entries (fewer machines first, then receipt, then hash), on a legacy entry without the field, and that a forged `finalMachines` in the payload is ignored; histogram `around` and `rank` agree with `/board`; board e2e shows the rule text; Minimalist's interaction (fewer machines is also the tie-break) is stated in the badge text.

**0.5.6 Sweep, migration rehearsal, release of rules v3** — S/M, merges `rules-v3`. *What:* paired sweeps with the generalised tool over 40 seeds × 120 tries for Sieve, reroll and the tiered pool, each measured alone and combined; `docs/baselines/0.5/` committed; DESIGN decisions log updated with the numbers and the go/no-go of each; golden corpus v3 generated, v2 archived; the 0.5.0 migration exercised against the captured v2 profile and a real browser profile; the deployment/rollback runbook written into `server/README.md` and rehearsed against a local verifier (deploy v3 bundle over a v2 board file, confirm v2 entries never rank, roll back, confirm v2 ranks again); title banner for one release; CHANGELOG 0.5.0 entry; tag. *Why:* PLAN-v1 0.5.5's gate, now with the review's "measure independently before combining" and an actual migration test. *Accept:* every `--gate` exits 0; dead-end seeds (no improving draft in any round) ≤ 2 of 20; `npm test` green including the archived-corpus refusal test and the migration fixture; the runbook's steps each have a recorded command and result in STATUS.

**0.5.7 ⚑ Fresh-player session on the decisions** — human, after 0.5.6. *What:* `docs/PLAYTEST.md` gains a v0.5 script: three fresh players, observe the Sieve decision (do they see the slag problem?), the reroll cost (do they reroll at $40, never, always?), and the tutorial; record quotes and timings; decide whether `rerollCost` or the Sieve weight moves (a v4 change) before v0.6. *Accept:* notes in `docs/playtests/`, decisions in DESIGN.

## 4. What the nightly routine may take

0.5.0 and 0.5.1 are `main` work and routine-safe (no rules change). 0.5.2–0.5.5 are `rules-v3` work: the routine may take them only on that branch, one increment per PR, each PR stating the rule it changes and the version it carries; it must not merge `rules-v3` or deploy anything. 0.5.6 and 0.5.7 are the owner's.

## 5. Metrics and risks

Watch: Sieve pick rate when offered (25–50 %), reroll rate per round (10–30 %), distinct machine-set signatures among the top 20 % of verified runs per daily (≥ 3 on most seeds), dead-end seed count (≤ 2 of 20), migration support questions (should be zero: the banner and the archived block explain it). Risks: the Sieve is a trap for greedy drafters (the "0 seeds worse" gate and the fixture guard it); reroll cost wrong in one direction (tune by the usage band before humans; a cost change is a v4); the branch lives long and drifts from `main` (merge `main` into `rules-v3` after every `main` increment; the golden corpus on both sides catches accidental rule drift); the review's own caveat that a bounded bot getting worse is not proof — report both policies and read the paired deltas, not the raw scores.
