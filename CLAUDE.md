# Junkyard Draft — project instructions

Two linked deliverables live in this repo:
1. **Junkyard Draft** — 2D factory score-attack game (TypeScript + Phaser 3.90 + esbuild). `game/`
2. **Workshop Control Room** — read-only live development dashboard fed by Claude Code hooks. `control-room/`, `.claude/hooks/`

Read `docs/STATUS.md` (what works, next task) and `docs/ROADMAP.md` (acceptance criteria) before changing anything. `docs/PRODUCTION-ROADMAP.md` is the plan of record from 0.7.0 to 1.0 (milestones, policies, the owner's decisions); `docs/DESIGN.md` holds the rules; `docs/CONTINUE.md` is the resume recipe.

## Rules of the road
- Player-facing words come from the string table and follow the glossary (0.9.0): yard, second, shift, checked, recording, the shelf, crews, "beat this", a try, your key; never seed, tick, verifier, replay, hash, histogram, percentile, reroll, bin, token (the policy page excepted). The lint fails the suite otherwise.
- `game/src/render/scenes/GameScene.ts` keeps only its 0.9.4 responsibilities (349 lines before the 0.9.5 Prettier pass, about 680 after it; do not grow it with new concerns): input belongs in `render/InputController.ts`, hints in `render/guide.ts`, sprites and per-tick effects in `render/SimView.ts` (+ the pure `render/simframes.ts`), the stall indicator in `render/StallMonitor.ts`, pops in `render/PopPool.ts`, the funnel in `render/GameTelemetry.ts`, the build overlay in `render/FlowOverlay.ts`; each has a unit test under `tests/`.
- Simulation (`game/src/sim/`) is pure, deterministic and browser-free. Rendering never influences outcomes. Bump `RULES_VERSION` when any rule or tuning value changes and keep replay verification tests green. Scenario namespaces (`tutorial-*`) are part of the rules: a change to what a reserved seed does is a rules change too (review F13). The golden corpus in `tests/golden/` pins existing replays; it is regenerated only together with a version bump.
- The tester build: `isTestEdition()` in `render/config.ts` is true when the baked server is `NO_SERVER`. It takes the game's offline paths at once, `useTestWords` swaps the words that would blame the connection, and what needs a server or a public address stays out of sight. A new screen that needs a server hides here too; `tests/test-edition-e2e.test.mjs` plays it as a stranger.
- Lessons (rules v5): `game/src/content/lessons.ts` is the script and `sim/yard.ts` holds the yards and the cards. A move names the part, the spot and what the part does; `render/guide.ts` shows the first one not made, `GameScene.onRail` refuses anything else, and the run is the only memory, so Undo just works. A new part the game can offer goes in a lesson or `tests/lessons.test.ts` fails. A lesson ends with its job done, so nothing is left unguided.
- Belts (rules v5): action `buy`, `RULES.beltCost` from the running score, never dealt in the offers (`RULES.draftWeights.conveyor` is 0). The price stays above `sellValue`. The evidence and the reasoning are in `docs/DESIGN.md`; `node --import tsx tools/belt-study.ts` measures it again.
- UX and copy (rules v4): `docs/UX-STANDARD.md` is the bar; `tests/strings.test.ts` holds the banned words, `tests/walkthrough-e2e.test.mjs` plays the lesson touching only what the game lights. One instruction at a time comes from `render/guide.ts` as text plus the spots to light; everything a player can touch has a `data-testid`. The way back in a game is to its first shift, never one shift (`docs/DESIGN.md`).
- Yards (rules v4): `game/src/sim/yard.ts` makes a seed's yard, job and shelf; `classic-*` seeds keep the old fixed starter for tests with fixed coordinates, `tutorial-1` is the lesson; a test on any other yard asks the layout (`tests/e2e/line.ts`). `node --import tsx tools/job-study.ts --seeds 60 --tries 120 --json docs/baselines/0.12/job-study-v5.json` recalibrates the stars.
- The yard for a screen reader (0.12.4): `render/mirror.ts` is pure and reads the same geometry as the flow overlay; a new thing on the yard is a line there. `tests/access-e2e.test.mjs` is the focus audit at phone width: a new screen goes in it.
- Layout (0.10.0): there is no fixed canvas size. The canvas fills `#game` (`render/viewport.ts`); the yard is drawn in board-logical px (`render/layout.ts`: `GRID_X/Y`, `CELL`, the shelf) and `GameScene.layoutBoard` fits the camera to the `.jd-board` slot the CSS-grid shell in `ui/GamePanel.ts` lays out by media query (`COMPACT_MQ`, `LANDSCAPE_MQ`, `TABLET_MQ`). DOM elements anchored to cells use `em(px)` with `--px` from the slot; chrome uses plain em. Tests never hard-code board coordinates: they use `page.jd.at()` / `drag()` with `cellCenter`, `binSlotCenter`, `shelfPoint` markers resolved from `window.__jd.geometry()`. Any layout change runs `tests/layout-e2e.test.mjs` (six viewports at 130 %) and keeps 46–50 px cells on a 390–430 phone; `MAX_BOARD_SCALE` stays 1 (a scaled sprite is a slower blit on the Canvas renderer; the perf gate on preset B measures it).
- Sharing (0.10.6): the results screen's "Share…" button exists only where `navigator.share` is a function and hands the sheet the same grid text Copy share text copies plus the card as a file; the GIF is the final layout and its strip says yard, score and the checked hash's first eight characters, never a hash for an unchecked run.
- The hub (0.11.10): `game/src/content/hub.ts` is the one list of categories; a category is one thread (`hub:<category>`), a topic `topic:<id>`, and both go through `threadTarget` like a day or a game, so a new kind of thread is a case there and nothing else. The plain pages are `server/community-page.ts`: no script, every player's word through `esc()`. `Pipeline.hubOpen` is a live count, not a setting.
- Direct messages (0.11.9): nothing reads a message unless the player it was sent to reports it, and `Pipeline.reportMessage` is the only thing that hands one to the classifier; the privacy notice says so, so no feature may read them in passing.
- Cosmetics (0.11.12): `game/src/content/cosmetics.ts` is the one list both sides read and an id starts with its kind; a new one is a line there and a `look.<id>` string, a title in the first-visit table because boards show it, the rest in `strings-more.ts`. The server decides what is earned (`earnCosmetics`) and a row in `cosmetics` stays, so a later change to the list takes nothing away. `render/paint.ts` swaps sprite aliases for recoloured canvases in `GameScene.init`, because `setTint` does nothing on the Canvas renderer: a new sprite that should take paint is a key in its lists, and materials are never painted. Nothing under `game/src/sim` may import any of it (`tests/cosmetics.test.ts`).
- The author card (0.11.13): `GET /card` by `hash` or `postId`, `Verifier.cardOf`, `ui/PlayerCardPanel.ts` (`render/playercard.ts`; `render/card.ts` is the share picture, a different thing). Players read the word profile. `accounts.card_private` leaves exactly `{ ok, player, friendable, private }`, and a block reads the same field for field. A new thing on a card goes behind that check, and a game on it behind the reveal gate. Who a run belongs to in `createServer` is `runOwner`, never `verifier.ownerOf`: a run from before a device signed in is stored under the device's id. `ColdStore.summaryOf` is the only way a public page reads across months.
- Friends (0.11.8): a player is reached through a run or a post and known afterwards by `friendHandle`, which means something only to its viewer, so no community route hands out a player id (the boards have carried `playerId` since 0.6.0: a hash of the device key, and reports read it). A block hides both ways and is never announced: a new surface that shows one player to another reads `CommunityStore.blockedWith`. `activity` feeds `/feed` and stays bounded per player; `feedLine` keeps the reveal gate.
- The day's talk (0.11.5): `ui/ThreadPanel.ts` behind `import()`, `render/thread.ts`, `GET /thread` through `postView`, so no player id leaves the server and a post's state reaches only its author. The reveal gate covers the words as it covers the recordings. The game shows a way in only when the server says there is one (`talk` on `/daily` and `/verify`), so with writing off Home is unchanged. Sal's posts and the web page's words are in `game/src/content/sal-posts.ts`, not the table, because the server writes them and must not carry the whole table; `tests/strings.test.ts` holds them to the glossary. `tests/e2e/standins.mjs` is the shared stand-in for the classifier and the mail service, and signs a page in.
- Moderation (0.11.2): `server/moderation.ts` is the one way free text reaches the store; a new writable field is a row in `TEXT_FIELDS` (`server/verify.ts`), one `textProblem` call and a push in `tests/moderation.test.ts`, and nothing but the pipeline calls `addPost`. Tests use a stand-in classifier (`ANTHROPIC_API_URL`), never the real service, because a run costs money; `node --import tsx tools/moderation-corpus.ts --live` is the one thing that calls it, with the owner's key. The call is a plain `fetch` so the verifier gains no dependency. Changing `RUBRIC` changes what the corpus measures: rerun it. The classifier failing goes to the queue, never to publish. A new reason code needs a sentence in `game/src/content/strings-more.ts`. The queue page holds no data and sets players' words only as text.
- Strings behind import() (0.11.2): `game/src/content/strings-more.ts` holds what only the lazily loaded panels read, so a new panel's text weighs nothing on a first visit. A module that needs a key there imports the file; `tests/strings.test.ts` walks the static imports from `main.ts` and fails when a first-visit module reaches it.
- Email sign-in (0.11.1): `server/link.ts` holds the rules and the one Resend request; `RESEND_API_KEY` turns it on, like the VAPID keys, and tests use a stand-in (`RESEND_API_URL`), never the real service. A device keeps its own key and `device_keys` says who its hash stands for: read a bearer through `bearerPlayer`, never `playerIdFromToken` directly. `render/sync.ts` merges so that nothing a device earned is lost; a new thing worth carrying goes on `SyncData`. Text size and picture quality stay on the device.
- Inbox (0.11.7): `CommunityStore.notify` writes a line (the same unread line once); `inboxLine` in `createServer` turns ids into names at read time, so no player id or crew code leaves the server; `content/inbox.ts` says what a line says, and a kind it does not know says nothing. A new kind is a line in both.
- Divisions (0.11.11): `game/src/daily/divisions.ts` is pure and the client only reads; `Verifier.onFreeze` hands the final board to `CommunityStore.closeDay` once, wired in `createServer`. A division's name is a key (`foundry-2`), `content/division.ts` makes it words. Trophies never decay: Home writes what it hears to local storage (`recordTrophies`) and Your record reads that.
- Reactions (0.11.3): `game/src/content/reactions.ts` is the fixed list both sides read; `ui/ReactionBar.ts` loads its own counts from `/entry` and shows nothing when the server cannot be reached. A watch is counted in `GET /replay` with a bearer, never for the run's own player. Your record stays local: the results write what they learn (`recordWatched`), the page never fetches.
- Fairness (0.12.5): `rank()` is what every board, medal, chart and division reads, so a filter there reaches all of them; a new board-like surface reads it too. A signal is noted for a person and acted on by nothing, and an identical game is refused before simulation, so anything about duplicates belongs at that refusal. A file kept outside the board (`voided/`) is in the export and reached by `deletePlayer`.
- Community (0.11.0): everything social lives in `server/community.ts` on `node:sqlite`, loaded on first use so the tools that import the verifier print no experimental warning. A migration is a new numbered module in `server/migrations/` plus a line in `index.ts`; it only adds, and an applied one never changes. A new column that holds a player id goes on `PLAYER_COLUMNS` (`tests/community.test.ts` walks the schema). Free text reaches the store only through the moderation pipeline (0.11.2). On Windows a running verifier locks the database: a test waits for the process to exit before deleting its data directory.
- The perf gate reads the whole run's script time, because a slow host draws fewer frames and each does more. Runners still differ, so a baseline comes from several runs through `tools/perf-baseline.ts`: the middle total and the worst drop rate, never one artifact and never this machine. A yardstick timed in the page was measured and made it worse: do not bring it back.
- Push (0.10.4, per kind 0.11.7): `server/push.ts` sends one message a day, "The yard is open"; a device can also ask to hear a reply or a beaten score, off until asked, `SOCIAL_PER_DAY` at most, none at night, in words that say neither who nor what, and those start from `CommunityStore.onNotify`, so a writer does not ask; `web-push` is the only runtime dependency (the production roadmap's rule 6: one at a time, by decision, recorded in `server/README.md`); the verifier needs `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` (⚑ the owner's) or the push routes answer 503. `tests/push.test.ts` holds the request format against a mock endpoint; never test against a real push service.
- The web app (0.10.3): `game/sw.js` is a template the build fills (`scripts/build-lib.mjs`); a new static file under `game/public/` joins the shell cache by itself, a new route or origin does not (other origins are never cached). The dev server serves no worker (`?sw=1` registers one in dev). `node tools/make-icons.mjs` re-renders `game/public/icons/` from `desktop/build/icon.svg`. The title is the only screen that announces a waiting update or offers the install (`render/pwa.ts`); `tests/pwa-e2e.test.mjs` must keep playing offline from the cache and rolling an update over between runs.
- Phaser (0.10.2): a new Phaser feature (a game object, a loader type, a scene plugin, a namespace) is a `require` in `game/phaser-entry.cjs` or it does not exist at runtime, whatever TypeScript says; what a first visit loads must stay under 300 KiB gzip (`tools/bundle-size.ts`, gated in `perf.yml`): a screen most visits never open goes in `ui/lazy.ts` behind `ui/panels.ts`, the one lazy entry, because each separate `import()` cuts what it shares with the game into small chunks a first visit pays for; long data takes an `import()` of its own, which shares nothing. Home is DOM and comes up before the sprite sheet: anything drawn from the sheet on the way from Home goes through `withArt` (`ui/opening.ts`). The entry needs the npm package's `src/` (the sandbox's `vendor/phaser` has only `dist/`).
- Input (0.10.1, keys move 0.12.4): `game/src/content/controls.ts` is the one action table, and a slot is one key of one action: a handler hears its slot's own key, so `loadKeyMap` changes what fires it and nothing else. Never `kb.on` a key outside that loop: Phaser replays its queue within a frame, and the loop is what hears an event once. Every dialog goes through `ui.layer`, which holds Tab inside it, so a dialog keeps no Tab list of its own. A new shortcut or gesture is a row there (its keys bind from the table in `render/InputController.ts`; the Tips panel and the build panel's keyboard line read the same rows); mouse, touch and keys all end in the same rule-checked actions. `tests/touch-e2e.test.mjs` must still play six rounds with touch events only.
- The record page (`ui/RecordPanel.ts`, 0.9.7) reads local storage only; the standings, medals and kinds it shows are written where the game learns them (`recordStanding`, `recordMedal`, `recordKinds` in `render/storage.ts`), never fetched.
- Scores are local and unverified until a server re-simulates replays. Never label local bests as verified; never invent competitors.
- Dev-only hooks (`window.__jd`) exist for automated play. They apply rule-checked actions and carry no scoring authority.
- Every meaningful increment: implement → `npm test`/typecheck → launch and exercise in Chromium → look at the screenshot → commit → `emit.mjs checkpoint` → update `docs/STATUS.md`.
- Keep Control Room instrumentation alive: emit `objective` when the goal changes, `task` on stage changes, `check` only from actual results, `screenshot` for captures, `checkpoint` on commits. Raw telemetry (`.control-room/events.jsonl`, screenshots, reports) stays out of Git.
- Never fabricate test results or screenshot observations. If a check cannot run, say so in STATUS.
- Commit messages end with the Co-Authored-By / Claude-Session trailer used in the existing history.
