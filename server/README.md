# Replay verifier (server/)

The trusted side of scoring: it re-simulates submitted replays with the same rules as the client and
keeps only verified scores. One Node process, a JSON file for storage, no database.

## Endpoints
Protocol level 2 (PLAN-v3 §1, reported by `/health`): identity is additive. A client may send `Authorization: Bearer <32 hex>` (its random device token; the server only ever uses `player_id = SHA-256(token)` and never stores or logs the token; the game sends it only to https or loopback verifiers). Anonymous submissions keep working exactly as before and legacy entries are never claimable.

| Method | Path | Returns |
|---|---|---|
| POST | `/verify` `{ replay, player? }` (+ optional bearer) | `{ ok, score, entry, recorded, player }` or `{ ok: false, error }` (422 rejected, 429 rate-limited per IP and, with a bearer, `PLAYER_RATE_LIMIT` = 2/min per player, 413 too large). With a bearer the entry is stamped `playerId` and `name#tag`, and **one best entry per (seed, player)** is kept: a better run replaces the earlier entry and its replay, an equal or worse run is verified but answered with `recorded: false` and the kept entry. A run on a minted daily seed after its `closesAt` is still re-simulated and answered `{ ok: true, score, late: true, recorded: false, closesAt }`: visible to the player, never on the final board |
| POST | `/identity` `{ name }` (bearer required) | claim or rename the display name: normalised (NFKC, whitespace, control characters, ≤ 32), refused by a folded blocklist (422), renames at most once per 24 h (429 + Retry-After); `{ ok, playerId, name, tag, createdAt, renamedAt }`; the tag is 4 confusable-free characters derived from the player id; a rename follows the player onto the boards |
| GET | `/identity` (bearer) | the claimed record, or 404 with `{ playerId, tag }` before any claim |
| DELETE | `/me` (bearer) | forget the player: name removed, their entries anonymised as `deleted`, their replays dropped; `{ ok, anonymisedEntries }` |
| GET | `/board?seed=…&limit=20` | verified entries for a seed |
| GET | `/daily?limit=10[&date=YYYY-MM-DD]` | the **minted** daily (PLAN-v3 0.6.1): `{ ok, date, seed, commitment, issuedAt, closesAt, minted: true, verified: true, entries, previous: { date, seed, commitment }, botPar, tieBreak }`. `seed = daily-<date>-base32(HMAC-SHA256(DAILY_SECRET, date))[0:8]`, issued on the first request on or after 00:00 UTC and stored; `commitment = SHA-256(seed(date+1))`, so tomorrow's seed is fixed before anyone can play it (`tools/mint-check.ts` verifies yesterday's commitment against today's seed). A `date` that has not opened is **403**; a malformed one 400. Submissions on a minted seed are accepted only if this server issued it and `now < closesAt` (48 h after 00:00 UTC; 0.6.2 adds freeze and archive). The client's `daily-YYYY-MM-DD` is the unranked practice seed: an ordinary seed board that never reaches `/daily`. **Window (0.6.2):** `closesAt` = 48 h after 00:00 UTC of the date; from then on the response carries `final: true` and `frozenAt` (= `closesAt`, set when first observed, idempotent, persisted) and the board never changes; `now` is the server clock so clients can say "closes in 31 h" |
| POST | `/groups` `{ name }` · `/groups/join` `{ code }` · `/groups/leave` `{ code }` · `/groups/rename` `{ code, name }` · `/groups/disband` `{ code }` (bearer) | groups (PLAN-v4 0.7.2): a code (8 base32 chars, never enumerable) scopes boards to its members; names pass the player-name filter (422), at most 5 groups per player and 50 members per group, creator-only rename (24 h cooldown, 429) and disband, a leaving creator hands over, the last leaver removes the group, 5 calls/min per player; `GET /groups` lists mine |
| GET | `/weekly?limit=10[&week=YYYY-Www]` | the **minted weekly** (PLAN-v4 0.7.5): the same shape as `/daily` plus `kind: 'weekly'`, `week`, `opensAt`; `date` is the Friday it opened. `seed = weekly-<week>-base32(HMAC-SHA256(DAILY_SECRET, "weekly:" + week))[0:8]`, issued on the first request at or after Friday 18:00 UTC and stored under the week id; `commitment = SHA-256(seed(next week))`, and the Friday's `/daily` record carries `weeklyCommitment = SHA-256(seed(this week))`, so `tools/mint-check.ts` checks the weekly chain beside the daily one. `closesAt` is seven days after the open; freeze, medals, the reveal gate, late answers, cold storage and the archive (where the week appears with `kind: 'weekly'` and `key: <week>`) are the daily pipeline. A week that has not opened is **403** (with `currentWeek`); a malformed or impossible week id 400 |
| (filter) | `?group=<code>` on `/board`, `/histogram`, `/daily`, `/weekly`, `/archive` (bearer) | entries limited to members' player ids with ranks and percentiles recomputed over them; 401 without a bearer, one 403 for an unknown code or a non-member; anonymous entries are never in a group; the response carries `group: { code, name }` |
| POST | `/report` `{ playerId \| hash, reason }` (bearer of a player with a claimed name) | name moderation (PLAN-v4 0.7.7): `reason` from `offensive, impersonation, personal-info, spam, other`; the target by player id or by the hash of one of their verified entries (anonymous entries 422); the reported name shows as `player` on every board, `/entry` and `/replay` until a moderator acts, scores untouched; one report per reporter per target (`duplicate: true`), 5/min per player, 404 unknown target, 422 self-report or off-list reason; `{ ok, playerId, hidden, duplicate }`. Once a name was cleared twice, further reports are recorded but no longer hide it. `GET /identity` carries `hidden: true` for the reported player |
| GET/POST | `/moderation/reports` · `/moderation/clear` `{ playerId }` · `/moderation/rename` `{ playerId, name }` · `/moderation/rename-group` `{ code, name }` (header `X-Moderation-Token`) | moderator endpoints, 403 unless the verifier runs with `MODERATION_TOKEN`, 401 on a wrong token: the list (reported and current name, hidden since, clears, reports), clear (shown again, reports closed), force a display or group name (filtered like any player-written name; the rename cooldown restarts). Every report and action appends one JSON line to `moderation.jsonl` next to the board (`MODERATION_FILE` overrides). `tools/moderate.ts` wraps them |
| GET | `/entry?hash=…[&seed=…]` | one verified entry for a challenge link (PLAN-v4 0.7.1): `{ ok, seed, score, player, rounds[], replayHash, verifiedAt, rulesVersion, frozen, medals }` — `rounds[]` are the per-round earnings derived at verification (stored on the entry like `finalMachines`, backfilled from stored replays at startup, never from the payload); no actions, so an open daily leaks nothing the reveal gate protects; 404 for an unknown hash and 404 `reason: 'no-rounds'` for a pre-0.7.1 entry without a stored replay; `seed` helps find a cold entry whose replay was compacted |
| GET | `/archive?from=&to=&limit=30` | closed days newest first (PLAN-v3 0.6.2): `{ ok, days: [{ date, key, kind: 'daily' | 'weekly', seed, closesAt, frozenAt, n, botPar, medals, top: top five entries }], nextTo }` (0.7.5: a weekly sorts by the Friday it opened and comes before that day's daily; `key` is its week id); `medals` (0.6.4) = `{ n, bronze, silver, gold }` set once at freeze from the final board as the 50th/80th/95th nearest-rank percentiles (`threshold(p) = sorted[ceil(p/100·n) − 1]`, ties earn the medal), or `null` below 5 runs; `/daily` carries the same field after freeze and `/histogram` returns it for a frozen daily seed; `nextTo` is the next older date to pass as `to` for the following page (null at the end); `from`/`to` must be `YYYY-MM-DD` (400); limit ≤ 100 |
| GET | `/histogram?seed=…&hash=…` (also `/board`, `/daily`: `botPar`) | verified score distribution for a seed: `{ n, step, bins[{from,to,count}], mine{score,rank,bin,percentile}?, around[] }` — the player's own entry located by replay hash, never by name |
| GET | `/replay?hash=…` (+ optional bearer) | the stored actions of a **verified** entry `{ ok, hash, seed, player, score, rulesVersion, actions, verifiedAt }` (404 otherwise). **Reveal gate (0.6.6):** on an open minted daily, 403 `{ reason: 'reveal-gate', error, closesAt }` unless the bearer's player has a verified entry on that seed; closed days, ordinary and practice seeds are never gated |
| GET | `/health` | `{ ok, version, rulesVersion, protocol, entries, entriesAllVersions, uptimeSec }` |
| POST | `/events` `{ installId, consent: true, events[] }` | opt-in funnel events (PLAN-v1 0.3.7): only the fixed vocabulary in `game/src/telemetry/events.ts`, consent explicit, ≤ 100 events, 30 req/min/IP; appended to `events.jsonl` with a daily-salted IP hash (422 rejected, 429 limited, 503 storage) |
| GET | `/funnel` | unique installs per first-session step and event counts (what `npm run funnel` prints from the file) |

## Run
```
npm run verifier                       # dev: tsx, 127.0.0.1:4400, board in server/data/board.json
npm run verifier:build                 # esbuild → server/dist/verify.mjs (single file, Node ≥ 20, no tsx)
node server/dist/verify.mjs --host 0.0.0.0 --port 4400 --data-dir /data --cors-origin https://your.site --rate-limit 60
```
Bot par (PLAN-v1 0.4.5): the first request about a seed starts the shipped autoplayer in a worker thread (5 searches × 40 tries, fixed rng streams, so the same number on every machine); the median is stored as `botPar` and returned by `/board`, `/histogram` and `/daily` (null while computing). `BOT_PAR=0` disables it, `BOT_PAR_CAP_MS` (20000) caps a job; a failed or capped job backs off ten minutes. It is a target labelled as a bot, never an entry.

Discord (PLAN-v4 0.7.6): `DISCORD_WEBHOOK_URL` (or `--discord-webhook`) makes the verifier post one short message to that webhook when a daily or weekly opens, when an open event gets a new #1 and when an event freezes (with medal thresholds); one per event type per seed, no mentions, a 429 honoured with `Retry-After` (three retries), other failures logged and dropped, never awaited by a request. `DISCORD_DRY_RUN=1` (or `--discord-dry-run`) prints instead of posting. `/health` carries `discord: { posted, dropped, deduped, retried }` when on.

Name moderation (PLAN-v4 0.7.7): `POST /report` is always on; `MODERATION_TOKEN` (or `--moderation-token`) enables `GET /moderation/reports` and `POST /moderation/clear|rename|rename-group` for `node --import tsx tools/moderate.ts <url> list|clear|rename|rename-group … --token T`; the audit log is `moderation.jsonl` next to the board (`MODERATION_FILE`). The appeal address on the policy page is a placeholder (`APPEAL_CONTACT` in `server/verify.ts`) the operator replaces before hosting.

Env vars with the same meaning: `HOST`, `PORT`, `DATA_DIR` (or `BOARD_FILE`), `EVENTS_FILE` (default next to the board), `EVENTS_RETENTION_DAYS` (30), `CORS_ORIGIN`, `RATE_LIMIT`, `PLAYER_RATE_LIMIT` (2), `DAILY_SECRET` (or `--daily-secret`; without it the verifier generates one into `<data dir>/daily-secret` with mode 0600 and says so: **back it up**, the ranked daily seeds derive from it). Rotating the secret keeps every issued day (their seeds are stored) but the commitment published on the last day under the old secret will not match the first day under the new one; `tools/rehearse-rollback.ts` rehearses the rotation
(POST /verify per client IP per minute), `TRUST_PROXY=1` (behind a reverse proxy you control: the client is `X-Real-IP`, else the **rightmost** `X-Forwarded-For` hop, the one your proxy appended; 0.8.1), `VERIFIER_LOG=0` (silence the request log), and the 0.8.1 knobs `READ_RATE_LIMIT` (300 GETs/min/address, `/health` exempt), `WRITE_RATE_LIMIT` (30 identity/group/report/deletion calls per minute per address), `MAX_PLAYERS` (20,000 claimed identities; over the cap the oldest that never submitted and sit in no group are evicted, else `POST /identity` answers 503), `REPORT_HIDE_REPORTERS` (2), `REPORTER_ESTABLISHED_DAYS` (7; `0` lets any named player count), `HIDE_EXPIRY_HOURS` (72).

0.8.1 also: the request log is one JSON object per line `{ ts, id, ip, method, path, status, ms }` where `ip` is a 16-hex daily-salted hash (never the address) and `group=` codes are redacted to `~`; every response carries `X-Request-Id` and every 500 logs its exception with that id to stderr; header/request/keep-alive timeouts are 15 s / 30 s / 5 s; SIGTERM or SIGINT stops accepting, lets in-flight requests and queued Discord posts finish and exits 0 (hard stop after 10 s); past dailies and weeklies can be asked for at most 400 days back (`historyStart` in `/health`); `/health` adds `hotFileBytes`, `lastCommitMs`, `commits`, `players`, `coldBytes`, `par { busy, queued, failures }` and `limiters { ip, player, read, write, events }` (the SQLite trigger's inputs); `DELETE /me` also drops the player's kept cold replays (`coldReplaysDropped`); opt-in events keep their address hash 7 days. Name moderation: a report hides a name only when two established reporters agree (or a moderator `confirm`s), an unconfirmed hide lapses after 72 h, `POST /moderation/confirm` and `tools/moderate.ts confirm` make it stand.

## Docker
```
docker build -t junkyard-verifier .
docker run -d --name verifier -p 4400:4400 -v verifier-data:/data -e CORS_ORIGIN=https://your.site junkyard-verifier
```
CI builds the image on every push, starts it on a named volume, runs `tools/image-smoke.ts` and `tools/mint-check.ts` against it, restarts it and checks the entry survived, and (0.8.1) pipes `docker logs` through `tools/log-check.ts` to prove no address and no group code reached the request log.

## Re-simulation (0.8.2)
A submission is prepared on the event loop without simulation (decode, rules version, an identical duplicate, an unissued minted seed → 422 with a `code`), re-simulated **once** in a persistent worker thread (`RESIM_CAP_MS` 10,000 ms cap per job; `RESIM_QUEUE` 32 submissions waiting behind the running one, beyond which `POST /verify` answers 503 `busy` with Retry-After 5; a job over the cap answers 422 `resim-timeout`; neither records anything), then recorded on the loop (window, keep-best, retention, commit). `RESIM_INLINE=1` keeps the single pass on the event loop (debugging). Every refusal from `/verify` carries a `code`: `bad-replay`, `rules-version`, `duplicate`, `unissued-seed`, `illegal-action`, `unfinished`, `did-not-reproduce`, `resim-timeout`, `busy`, `rate-limited`, `too-large`, `bad-request`, `storage`. `/health` reports `resim { jobs, timeouts, queued, busy, capMs, maxQueue }`. Boards keep a per-seed sorted index, so reads and the retention pass no longer sort the whole board. `node --import tsx tools/load.ts <url> [--rate 60] [--ips 3] [--minutes 2] [--budget 100] [--json out]` floods a verifier started with `TRUST_PROXY=1` from simulated addresses and samples `/health`; the 0.8.2 baseline is `docs/baselines/0.8/load-0.8.2.json`.

## Pointing the game at it
`VERIFIER_URL=https://verifier.your.site npm run build` bakes the URL into `dist/` (default
`http://127.0.0.1:4400`). A `?verifier=` query parameter overrides it at runtime **only in dev builds and on pages served from a loopback host** (tests and local setups); a hosted build ignores it, so a link can never point a player's client, and its bearer token, at another host (production roadmap 0.8.0, `game/src/render/config.ts`). The built page also carries a Content-Security-Policy whose `connect-src` names the baked verifier origin, so the hosted verifier's origin must match `VERIFIER_URL` exactly (scheme, host, port).

## Storage: measured headroom and the SQLite trigger (PLAN-v3 0.6.7)
The board is one JSON file rewritten atomically on every commit. The policy trigger for moving to SQLite is **5 MB on disk or 50 ms per commit**. `tools/storage-measure.ts` synthesises boards in the post-retention shape (≤ 1000 entries and ≤ 100 stored replays per seed, one identity per player, one record and one par per day) and times the real commit path; baselines on the dev PC (Ryzen 9 9950X3D, Node 24, Windows) in `docs/baselines/0.6/`:

| players × days | entries | replays | file | load | commit (median) | status |
|---|---|---|---|---|---|---|
| 100 × 30 | 3,000 | 3,000 | 2.5 MB | 12 ms | 9 ms | within |
| 1,000 × 30 | 30,000 | 3,000 | 10.9 MB | 31 ms | 30 ms | **size trigger crossed** |
| 10,000 × 30 | 30,000 (capped) | 3,000 | 12.5 MB | 43 ms | 33 ms | **size trigger crossed** |
| 10 × 365 | 3,650 | 3,650 | 3.2 MB | 14 ms | 13 ms | within |
| 100 × 365 | 36,500 | 36,500 | 30.2 MB | 165 ms | 128 ms | **both triggers crossed** |

**Hot/cold split (PLAN-v4 0.7.0).** Frozen dailies older than `HOT_DAYS` (30) leave the hot board at startup and once an hour for `cold/YYYY-MM.json` (every entry, the day record with medals, the par, and only the top `COLD_REPLAYS_PER_DAY` (10) stored replays; `cold/index.json` maps seed → date and kept replay → date; months load lazily through a 3-entry LRU). Boards, histograms, medals, pars, `/daily?date=`, `/archive` and `/replay` answer for cold days exactly as before; a compacted replay is 404 `{ reason: 'compacted' }` when the seed is given; names on cold boards resolve against current identities, so renames and `DELETE /me` need no cold rewrite; the commit path writes the hot file only. Measured with `tools/storage-measure.ts --split` (`docs/baselines/0.7/`):

| players × days | whole board | after split: hot file | hot commit (median) | cold files | status |
|---|---|---|---|---|---|
| 10 × 365 | 3.2 MB | 0.4 MB | 1.3 ms | 3.2 MB | within |
| 100 × 365 | 30.2 MB / 118 ms | **4.0 MB** | **9.8 ms** | 12.4 MB | within |
| 1,000 × 365 | 131 MB / 448 ms | 13.8 MB | 35.6 ms | 103 MB | **hot size over** |
| 100 × 60 | 5.0 MB | 4.0 MB | 9.8 ms | 1.1 MB | within |
| 1,000 × 60 | 21.7 MB / 61 ms | 13.8 MB | 28.9 ms | 9.3 MB | **hot size over** |

The hot file is now bounded by players, not days: ≈ players × 30 days × 310 B, so it crosses 5 MB at roughly **550 daily players** regardless of how long the service has run, while commit latency stays under 50 ms to at least 1,000 players on this machine. The one-off split of a year's backlog takes ~1 s per 100 players. **Decision:** the beta runs on JSON with the split; 0.7.0b (SQLite behind the same `Board` interface) is scheduled, not optional, when a measured month shows the hot file above 5 MB, i.e. around 500 daily players.

What the earlier whole-board numbers say: an entry costs ~310 bytes and a stored replay ~700 bytes; the per-seed caps bound each day, but every daily is a new seed, so the file grows without bound in *days* (about 85 KB per day per 100 players). A web beta of up to ~100 daily players stays under the trigger for roughly two months; 1,000 players cross the size trigger inside a month while commit latency is still fine (~30 ms at 11 MB on this machine, slower on a small VPS). Decision recorded here, not guessed: **storage stays JSON for the 0.6.8 beta; the first v0.7 storage item is either SQLite or archive compaction** (keep every frozen day's entries, drop stored replays below the top 10 once a day is older than ~30 days: replays are two thirds of the year-long file), to be chosen with the beta's real numbers. Re-run the tool after any change to retention or the entry shape.

## Guarantees (each pinned by a test in `tests/verifier.test.ts`)
- A malformed request never kills the process: unparsable URLs get 400, handler errors 500, socket-level garbage 400 via `clientError`.
- Nothing is recorded until it is on disk: the candidate board is written to a temp file in the same directory and renamed over
  `board.json`; a failed write leaves memory and disk unchanged and the client gets **503 + Retry-After** (the retry is not a duplicate).
- Boards are partitioned by rules version: rows persisted under another `RULES_VERSION` stay in the file but never rank, count or replay.
- Replay identity is SHA-256 over `{ rulesVersion, seed, actions }`; legacy 8-hex ids from earlier boards still resolve for playback.
- Bounded resources: body ≤ 512 KB, query limits are finite integers clamped to [1, 100] (`/board`) and [1, 50] (`/daily`), rate-limiter
  cardinality ≤ 10,000 keys, replays kept for each seed's top 100, entries ≤ 1,000 per seed, ≤ 5,000 seeds (least recently active dropped).
- A damaged `board.json` loads as an empty board with bad rows dropped, rather than preventing startup.
- Groups (PLAN-v4 0.7.2): create/join/leave/rename/disband with the caps and the name filter, a scoped board equals the members' entries in rank order with the histogram rank recomputed, unknown codes and non-members get one 403, `DELETE /me` removes memberships and hands a creator's group to the next member.
- Reveal gate (PLAN-v3 0.6.6): `/replay` on an open daily is 403 without a qualifying bearer, 200 for a player with an entry, 200 for everyone once the day closes, and never gated for ordinary seeds.
- Medals (PLAN-v3 0.6.4): computed exactly once at freeze (days frozen before medals existed get them on the next observation), never while a day is open, null below five runs; the exact percentile math is pinned by `tests/medals.test.ts`.
- Daily window (PLAN-v3 0.6.2): freeze flips exactly at `closesAt` with a fake clock, is idempotent and survives a restart; late submissions answer `late` and stay off the board and out of the replay store; the archive lists frozen days only, newest first, paged by `limit`/`nextTo`; a day's bot par is never dropped by the par cap.
- Identity (PLAN-v3 0.6.0): the bearer token is hashed before any use and appears in no log line; tags are deterministic per player id; the rename cooldown, name refusals, keep-best replacement (entry and replay), the equal-run case, the per-player bucket and `DELETE /me` are each exercised over HTTP.

## Rules-version deployment and rollback (runbook, rehearsed by `tools/rehearse-rollback.ts`)
A rules bump (`RULES_VERSION`) changes what the verifier accepts; entries and replays of every version stay in the board file and only the current version ranks.
1. Merge the rules branch to `main`, tag the release, build the bundle (`npm run verifier:build`) and the web/desktop builds from the same commit.
2. Deploy the new bundle over the existing data directory. Expect: `/health` reports the new `rulesVersion`, `entries` 0 for seeds with no new-version runs and `entriesAllVersions` unchanged; old-version replays are refused with `rejected: rules version N not accepted (server has M)`; old entries keep their replays (pruning never drops another version's replays).
3. Publish the web build and the desktop installer the same hour; the title's archived-bests block tells upgrading players that old replays and saves no longer verify.
4. Rollback: redeploy the previous bundle over the same data. Expect: the old version ranks again with replays intact; new-version entries stay stored and refused. Nothing is deleted in either direction.
`node --import tsx tools/rehearse-rollback.ts` performs steps 2 and 4 against bundles built from `main` (previous version) and the working tree, on a temporary data directory, and writes `docs/baselines/0.5/rollback-rehearsal.json`; run it before every rules release.

## Operational notes
- The default data directory is `<cwd>/server/data` for both the source run and the bundled run; set `DATA_DIR` (or `--data-dir`) in production.
- Rate limiting is a fixed window per process; behind several replicas use the proxy's limiter instead.
- The board file is rewritten on every accepted submission and now also holds each verified replay's actions (≤ 4000 actions, bounded at verification); keep it on a persistent volume. Boards written before replay storage simply have no replays (`replayAvailable: false`).
- Retention: stored replay actions are kept only for each seed's top 100 entries (the `/board` cap); lower entries keep their score but lose their replay (`replayAvailable: false`). Pruning happens on every write.
- Rules version mismatches are rejected, so deploy the verifier from the same commit as the game.
- Nothing authenticates players: `player` is a display name only. Abuse controls = rate limit + duplicate replay hash.
- Funnel events (`events.jsonl`): one JSON line per event with `at`, `receivedAt`, `installId` (random, client-generated, deleted when the player opts out), `ip` (16-hex SHA-256 of a per-process salt + UTC date + address: one key per client per day, unlinkable across days or restarts), `name`, `props`. No seeds except `daily-*`/`tutorial-*` labels, no layouts, no names. Rows older than the retention are pruned at start and hourly. Report: `npm run funnel -- path/to/events.jsonl`.
